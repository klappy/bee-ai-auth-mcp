# Production source deployment

Feature branches merge to main (staging). Production is promoted only by the reviewed main → production PR. Existing production Git Build runs `npm ci && node scripts/gen-version.mjs && npm run typecheck && npm test`, then `node scripts/deploy-production.cjs`. This source does not edit or invoke the provider trigger. Otto separately reviews and configures it.

## Accepted prerequisite manifest

`deploy/production-prerequisites.json` deliberately starts `accepted:false`. A reviewed PR must pin the real old active version/deployment, reviewed main ancestor, independent release receipt, exact desired full writable metadata and its public-config digest, exact approved nonsecret additions, accepted Access resources/policies, and the approved positive monthly limit/version. No default allowance, secret value, private identity or identity hash belongs in the manifest.

The source uploader is a combined first-hosted-release transaction. It never activates an old-source/new-config intermediate. Its base is the deployment-selected old active version, not the custody version or the legacy script/settings projection. The accepted custody version must contain the exact old module and preserved old metadata/bindings plus precisely CONSENT_SIGNING_SECRET and ADMIN_OWNER_EMAIL. Only those two new secret names inherit from its explicit version ID. Existing GitHub secrets inherit from the old active version ID. Request-level source selectors and provider-returned secret names/types are verified; GET cannot establish secret value equality.

The manifest's desiredMetadata must exactly match complete preserved supported metadata plus the accepted BeeBridge export/linkage normalization, with external assets deliberately absent. Its desiredNonsecretBindings must exactly equal the seven approved hosted bindings derived from the reviewed Access and monthly policy tuple. Extra fields/additions refuse. ACCESS_TEAM_DOMAIN is a hostname, `klappy.cloudflareaccess.com`; the JWT verifier itself constructs the HTTPS issuer. Neither observability nor logpush is supported by the Version POST schema, and those fields are explicitly rejected there.

## Effective logging and runtime prerequisites

Before this Build, Otto must complete the separately reviewed Container image/logging rollout and effective Worker logging-only configuration. The supported logging endpoint is GET/PATCH `/workers/scripts/bee-ai-auth-mcp/script-settings`; the uploader only GETs it. It verifies the exact desiredLogging snapshot: authoritative Worker observability.enabled, logs.enabled and traces.enabled explicitly false; logpush false, redact_query_string false, no tails or log/trace destinations, and all other observed fields/rates preserved. Full effective logging is compared before upload, immediately before deploy and after deploy. The provider normalizes script-settings observability to null while Worker GET exposes disabled enable gates and retained nested persist/invocation defaults. Null alone never passes; missing enable flags or export sinks refuse. The desiredLogging manifest pins the Worker logpush/observability snapshot, and loggingAcceptanceReceipt pins independent effective-state acceptance. The original attempted six-boolean preservation FAIL remains documented. Logging is not attributed to unsupported version fields. No settings PATCH, Container rollout, Access creation, secret generation or billing activation runs in this script.

Private max1/basic Container allocation, immutable image, separate production storage, narrow OTP browser routes, separate owner-admin policy and disabled preview URLs are also verified. The production admin's sole email selector is compared privately with the freshly read shape-validated existing staging owner policy. No email or hash is output. All actual public paths are bundled from canonical files; no external asset JWT, router, ASSETS binding or duplicate HTML source remains. Only the exact obsolete review banner is removed after accepted monthly prerequisites; staging retains its banner and all substantive approved copy remains unchanged.

## One candidate, then explicit deployment

The Build verifies its stamped CI commit and reviewed-main ancestry before provider reads. A shallow checkout is unshallowed with a bounded credential-free fetch from the fixed public repository and exact CI SHA; missing ancestry objects get one bounded fetch/recheck. Credentials and Git config are not dumped; interactive auth and inherited global/system config are disabled, output is captured, and HEAD must remain the exact CI SHA. This is read-only repository preparation, not provider deployment.

Upload uses deploy=false and combines reviewed hosted source, embedded assets, desired metadata, approved additions and exact secret inheritance. Candidate bytes, binding shape, metadata, no external assets and full DO/SQLite/Container lineage are checked before deployment. Cloudflare was observed omitting migration_tag on undeployed versions; absence is accepted only with complete unchanged lineage and no migration payload. Contrary tags refuse and actual deployed migration_tag must be v1. Actual active deployment/version, ingress, Access and logging are rechecked before an explicit 100% deployment.

Post-deployment checks verify exact source/version, version-selected bindings, effective logging, Container configuration/image, domain, untouched staging, all 16 public assets by bytes/MIME, HEAD, OAuth JSON and MCP challenge. They do not claim authenticated Bee, cross-user or grant-cleanup acceptance. A lost deployment response is reconciled through the active deployment; unavailable reconciliation reports unknown, not no effect. A deployed source whose readback fails remains a failed build. No automatic rollback or state deletion occurs.

Legacy script/settings may project the newest undeployed candidate. Its binding-match boolean is diagnostic and never supplies the active configuration. Provider receipts and evidence of the initially failed asset-preservation assumption remain in the meal envelope. The accepted combined transaction supersedes the earlier preactivated-configuration proposal; the logging-only prerequisite supersedes the unsupported version-scoped logging proposal.
