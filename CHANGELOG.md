# Changelog

## 0.3.0 — 2026-08-29

- **The email door (Cloudflare Access), beside GitHub — never replacing it.** Public `/authorize` is a chooser when Access vars are set (email + GitHub links, OAuth query preserved) and the original GitHub redirect when they are empty. `/authorize/email` is the only Access-protected route: it validates `Cf-Access-Jwt-Assertion` server-side (jose: `jwtVerify` + `createRemoteJWKSet` against the team's published certs, issuer + AUD pinned). A valid on-list email reaches consent; a valid off-list identity is denied (403) before consent renders; missing or invalid proof fails closed (403) with no silent GitHub fallback. `/authorize/github` and `/callback` stay independent. New vars: `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`. `ALLOWED_EMAILS` is a private Worker secret (unset/empty denies every email). Existing GitHub-login grants keep working with no reconnect (emails contain `@`, GitHub logins cannot — disjoint namespaces by construction).
- **`CONSENT_SIGNING_SECRET` (new REQUIRED secret).** The consent-state HMAC and the sealed pairing state rekey from `GITHUB_CLIENT_SECRET` to a dedicated secret; the GitHub client secret returns to single-use (OAuth code exchange only). Hard switch: consent/pairing states live minutes; an in-flight round-trip at deploy moment restarts. (`deriveTenantKey` in telemetry deliberately stays on the old anchor — rekeying it would rotate every historical tenant key.)
- **Hard rail preserved:** `/register`, `/token`, `/mcp` are never behind Access. The Access app is scoped to `/authorize/email` only. Shared `/consent` and `/pairing/*` stay outside Access and re-check signed identity against the matching allow-list.
- **Hosted Bee CLI is a one-shot auth broker, not a shared session.** The bound container still runs caddy as the token-agnostic data plane. Pairing execs the real Bee CLI under an opaque per-attempt `BEE_CONFIG_DIR`, shows the **CLI-generated** `https://bee.computer/connect#…` deep link/QR, transfers that invitee's bearer into their encrypted grant, and deletes the broker directory. Retry and expiry clear only that identity's previous dir (wrong sealed `p` is a no-op). `bee proxy` is forbidden (official local-dev only; one login injected onto every `/v1` request). Invitees do not install the CLI. The operator Bee login is never reused. Final broker image is `distroless/base-debian12:nonroot` + static caddy + compiled `bee` + compiled helper, `USER 65532:65532` — not a Debian/root toolbox. Token handoff is that helper’s one JSON exec line, then unlink; not a shell, not a shared proxy, not `createBeeClient` (login does not return the token). (`docs/hosted-cli-architecture-finding-2026-09-08.md`)
- **CI is truthful about this Worker shape.** Durable Object + Container Workers do not receive Preview URLs, and `versions upload` does not publish container images. Unit/typecheck remain the required PR gate. Deployed smoke runs only when repo variable `DEPLOYED_VALIDATION_URL` names an isolated Worker whose `/version` matches the PR head (SHA mismatch fails closed) — never production, never an impossible branch alias. Live production is the `production` branch (`bee.klappy.dev/version`), not merge-to-`main`.
- **Supported image probe.** `scripts/probe-bridge-image.sh` + `npm run test:image` fail-closed on a built `bee-bridge:local` (non-root, no shell/apt/bun, real `bee`, proxy forbidden, isolated `clear`). Absent docker/image is exit 2 (named skip), not a pass. (`docs/meal-debrief-2026-09-08.md`)

## 0.2.0 — 2026-07-19

- **Device-aware consent CTA.** The consent screen now adapts to the device it renders on: mobile leads with a tap-to-approve deep link ("Open in the Bee app"), with the QR collapsed behind an "Or scan a QR code" toggle; desktop keeps the QR as the primary action. Stale pairing actions (a dead approve link / connect URL / QR from an expired or failed attempt) are now cleared immediately on retry instead of lingering until the next pairing code loads.
- **Copyable connect URL.** Both device variants show a copyable connect URL (`https://bee.computer/connect#<requestId>`) for manual entry into the Bee app's "Enter Bee ID" field, alongside the existing raw-token paste fallback.
- **Pairing nested-token fix.** The pairing-completion parser now also accepts the Bee token nested under `result.encryptedToken`, in addition to the original top-level `encryptedToken` shape.
- **Sanitized shape diagnostics.** When the pairing service returns an unrecognized response shape, the error/log message now includes a redacted, truncated description of that shape (token/secret/key-like fields replaced with `<redacted:N>`) instead of a bare "unexpected shape" string, so failures are self-diagnosing without ever leaking secret material.
